# Delegation — briefing a thread and receiving its result

Read before `start_thread`, and before a `message_thread` that changes what a thread is assigned. The core's §Delegation lines still hold; this file lists the parts a brief is assembled from and what reception adds. §Delegation Handoffs in `rules/preferences.md` beside this directory is the general rule both come from.

## The parts of a brief

- **The goal, and the reading taken of choi's ask.** Attach choi's own messages by id rather than restating them; a paraphrase loses what choi actually said.
- **Where the work happens:** the repository, the folder on choi's device by its listed path, the PR branch.
- **The records to read:** project-file paths, thread links, session ids, PR numbers, the line of a record where a finding was observed.
- **What was already ruled out,** with where that was settled, so the thread does not reopen it.
- **Choices choi has not made,** left open as choices, with the options known so far.
- **Grants, by kind, target and limit,** with choi's answer quoted or attached. A brief without one gives none.
- **The result expected and where it lands:** an updated PR, a file under the project folder, a reply in the thread; and who merges.

## Left out of a brief

- A rule the thread already loads. A thread in an environment that runs `cloud-setup.sh` holds choi's rules; name a rule file only where it decides the work. A thread in an environment without it holds none, so the brief names the rule files the work turns on.
- A long derivation. It goes into a project file, and the brief points there.

## Receiving a result

- **A thread's recommendation keeps choi's selection.** Relay it as the thread's proposal with its ground; where analysis settles it, relay the conclusion.
- **The summary for choi leads with the outcome** in one or two sentences and links the thread or artifact. The detail stays where the thread wrote it.
